# Nomi 可执行优化计划

## 目标

把当前原型推进到可长期自用的 `Nomi 1.0 Alpha`：

- 只使用真实数据和真实工具，不编造结果；
- 所有会修改用户数据的动作都先预览、再确认；
- 具有短期上下文和可管理、可删除的长期记忆；
- 以 Nomi 和“今日”两个主入口承载对话、主动建议和任务结果；
- 先实现附近美食/酒店查询和官方页面跳转，不直接自动支付；
- 在真机连续使用 14 天，证明可靠性和留存后再接正式票务接口。

本计划默认：

- 平台为 iOS 17+；
- 模型仍使用 DeepSeek；
- 单人开发，按“专注日”估算；
- 当前仓库中的代码是起点，不假设产品已经通过 App Store。

## 架构决策

1. **单 Agent + 工具注册表**：暂不做多 Agent。一个编排器负责理解、计划和表达，工具负责真实操作。
2. **规则负责安全，模型负责理解与表达**：高风险动作必须经过确定性规则和本地/后端策略检查，模型无权直接删除、修改、预订或支付。
3. **所有副作用都有状态机**：准备动作、展示确认、执行、核验、生成回执；失败后先查状态，再决定是否重试。
4. **本地优先，云端受控**：个人偏好、聊天和记忆默认存本机；正式分发后通过自有后端代理模型和语音服务，不在客户端内置长期密钥。
5. **先做垂直闭环**：每一个阶段都交付一个可使用的端到端能力，不同时铺开所有页面和数据源。

## 产品调整

推荐把当前四个一级 Tab 收敛为两个：

```text
Nomi
  ├─ 当前状态与表情
  ├─ 一句话输入/语音
  ├─ 当前任务与选项
  ├─ 操作确认和回执
  └─ 最近结果

今日
  ├─ 今日简报
  ├─ 日程时间线
  ├─ 待办
  └─ 天气、步数和身体状态
```

“日程”并入“今日”；“设置、记忆、隐私、权限”进入 Nomi 头像下的个人菜单。Nomi 的表情用于表达 Agent 状态，不再只是装饰。

## Phase 0：安全止损

目标：在继续加功能前，先确保密钥、隐私和破坏性操作不会伤害用户。

### Task 1：撤销并清理第三方语音密钥

**描述：** 撤销当前已暴露的讯飞凭据，移除客户端和仓库中的长期密钥，并检查历史提交、脚本和文档。

**验收标准：**

- [ ] 讯飞控制台中的旧凭据已经失效。
- [ ] 当前工作树和 Git 历史中没有可用的真实凭据。
- [ ] 测试脚本只从环境变量读取凭据。
- [ ] 正式语音方案改为后端短期凭证或系统语音兜底。

**验证：**

- [ ] 使用关键词扫描当前工作树和历史记录，不输出密钥内容。
- [ ] 启动 App，系统语音仍可正常使用。

**依赖：** 无  
**预计工作量：** 0.5～1 天  
**风险：** 改写 Git 历史是破坏性操作，执行前必须单独确认备份和目标分支。

### Task 2：修正默认权限与隐私说明

**描述：** 摄像头默认关闭；日历、提醒、位置、通知按实际使用场景逐个申请；修正“不会上传”的不准确说明。

**验收标准：**

- [ ] 首次启动不自动打开摄像头。
- [ ] 只在点击对应功能时申请相机、日历、提醒和位置权限。
- [ ] 首次启动最多出现一个权限请求。
- [ ] 隐私页明确列出 DeepSeek、讯飞、天气和地图分别会接收什么数据。
- [ ] 记忆页区分“本机保存”和“发送给模型处理”。

**验证：**

- [ ] 删除 App 后重新安装，记录首屏实际出现的权限弹窗。
- [ ] 拒绝任一权限后，其余功能仍可运行。
- [ ] 对照代码与隐私页逐项检查数据流。

**依赖：** 无  
**预计工作量：** 1～1.5 天

### Checkpoint A：安全底线

- [ ] 无真实密钥进入仓库。
- [ ] 摄像头默认关闭。
- [ ] 隐私说明与代码一致。
- [ ] 未确认时不会删除或修改用户数据。

## Phase 1：动作安全与测试底座

目标：先让 Nomi “不会做错”，再让它“能做更多”。

### Task 3：建立 iOS 单元测试目标

**描述：** 在 XcodeGen 工程和 CI 中加入 XCTest target，覆盖规则、意图、时间解析和后续动作策略。

**验收标准：**

- [ ] `project.yml` 中存在 `JinriTests` target。
- [ ] CI 在构建前执行 `xcodebuild test`。
- [ ] `RulesEngine`、`ScheduleParser`、`ChatRouter`、`PetState` 至少各有一组测试。
- [ ] 测试失败时 CI 必须失败。

**验证：**

- [ ] 本地解析检查通过。
- [ ] macOS CI 中 `xcodebuild test` 通过。
- [ ] 故意破坏一条规则，确认测试能捕获。

**依赖：** 无  
**预计工作量：** 1 天

### Task 4：修复会议选择并加入确认流程

**描述：** 将“根据时间和标题选择会议”提取为可测试的 `MeetingTargetResolver`。找不到精确目标时追问，不允许回退到下一场会议。取消和改期先生成预览，用户确认后执行。

**验收标准：**

- [ ] 用户指定时间但目标不存在时，不选择其他会议。
- [ ] 多个候选时先让用户选，不自动猜。
- [ ] 取消和改期都显示标题、原时间、新时间和操作按钮。
- [ ] 未确认不会写日历。
- [ ] 连续点击确认不会重复执行。

**验证：**

- [ ] 测试“不存在四点会议时，不能删除五点会议”。
- [ ] 测试两个会议标题相同但时间不同。
- [ ] 真机完成一次取消、一次改期和一次主动放弃。

**依赖：** Task 3  
**预计工作量：** 2 天

### Task 5：统一动作预览、执行和回执

**描述：** 增加统一动作模型，后续完成待办、创建日程和预订都复用它。

**验收标准：**

- [ ] 动作至少包含 `description`、`riskLevel`、`payload`、`confirmationToken`。
- [ ] 执行结果区分成功、失败、状态未知、需要继续输入。
- [ ] 每次副作用都记录脱敏审计日志。
- [ ] 执行后展示可读回执，而不是只有一句自然语言。

**验证：**

- [ ] 单元测试覆盖低风险、高风险、重复提交和状态未知。
- [ ] 检查日志中不出现 API Key、完整地址或健康数据。

**依赖：** Task 4  
**预计工作量：** 1.5～2 天

### Checkpoint B：动作安全

- [ ] 测试全部通过。
- [ ] 所有破坏性动作都需要确认。
- [ ] 找不到目标时只追问。
- [ ] 重复点击不会重复执行。

## Phase 2：拆分 Agent 内核

目标：让新增一个工具不再需要修改 `AssistantView`。

### Task 6：定义 Agent 和工具协议

**描述：** 新增 `AgentTypes`、`ToolDefinition`、`ToolRequest`、`ToolResult`、`ActionPolicy`。

**验收标准：**

- [ ] 每个工具声明名称、输入 schema、输出 schema 和风险等级。
- [ ] 工具只能通过注册表被发现。
- [ ] 高风险工具必须声明确认策略。
- [ ] 工具输出统一为成功、追问、确认、失败四种状态。

**依赖：** Task 5  
**预计工作量：** 1～1.5 天

### Task 7：迁移现有日历、天气、位置工具

**描述：** 将 `AssistantView` 中的直接服务调用抽成 `CalendarTool`、`WeatherTool`、`LocationTool`，保留 `RulesEngine` 作为本地主动规则层。

**验收标准：**

- [ ] 视图不再直接调用 `CalendarService.deleteEvent` 等高风险 API。
- [ ] 同一工具无论从聊天还是快捷入口调用，行为一致。
- [ ] 原有天气、日程、位置卡仍正常工作。
- [ ] 模型不可用时，只读卡片和本地规则仍正常。

**依赖：** Task 6  
**预计工作量：** 2 天

### Task 8：建立 NomiAgent 和混合意图路由

**描述：** 固定高风险意图继续走本地规则；长尾对话交给 DeepSeek；所有模型工具建议都经过 schema 校验和 `ActionPolicy`。

**验收标准：**

- [ ] `AssistantView` 不再保存核心 system prompt 和业务决策。
- [ ] “取消、改期、下单、支付”不能绕过本地策略。
- [ ] 普通闲聊仍由 DeepSeek 回答。
- [ ] 工具调用失败时能回退到可解释的本地回答。

**验证：**

- [ ] 用至少 30 条中文指令跑离线意图测试。
- [ ] 测试“取消会议”不会被误判为普通聊天或创建日程。

**依赖：** Task 7  
**预计工作量：** 2 天

### Checkpoint C：Agent 内核

- [ ] `AssistantView` 只承担显示和用户交互。
- [ ] 工具与策略可独立测试。
- [ ] 新增只读工具时无需修改主视图。
- [ ] 高风险操作无法绕过确认。

## Phase 4：真实记忆和主动提醒

目标：从“记住聊天原文”升级为“理解并管理用户偏好”。

### Task 12：把聊天记录和长期记忆分开

**描述：** 保留 `ChatLog`，新增 `MemoryFact`；重要事实经过确认后写入，包含来源、可信度、创建时间和过期时间。

**验收标准：**

- [ ] 普通聊天不会自动变成永久记忆。
- [ ] 用户明确要求“记住”时生成一条待确认记忆。
- [ ] 记忆可以逐条编辑、过期、删除和导出。
- [ ] 敏感类别默认不自动保存。

**依赖：** Task 8  
**预计工作量：** 2 天

### Task 13：建立上下文组装器

**描述：** 为模型组装近期对话、相关长期记忆、当前数据卡、能力边界和明确的隐私过滤。

**验收标准：**

- [ ] 模型只收到与当前任务相关的记忆。
- [ ] 过期记忆不会进入上下文。
- [ ] 用户可以查看“这次对话给模型发送了什么”。
- [ ] 上下文超限时先摘要旧对话，不整体丢弃新状态。

**依赖：** Task 12  
**预计工作量：** 1.5 天

### Task 14：统一主动提醒预算

**描述：** 建立统一通知协调器，取代各功能独立排程；支持每日预算、去重、延后、关闭和动作。

**验收标准：**

- [ ] 默认每天最多 3 条主动通知。
- [ ] 同一事实 24 小时内不重复。
- [ ] 每条通知至少有一个动作。
- [ ] 连续忽略后自动降频。
- [ ] 用户可以从通知或 App 内解释“为什么现在提醒”。

**验证：**

- [ ] 构造 7 天模拟日程和天气，检查通知总数。
- [ ] 真机检查通知动作能回到正确页面。

**依赖：** Task 5  
**预计工作量：** 2 天

### Checkpoint E：记忆与主动性

- [ ] 用户能看见、修改和删除记忆。
- [ ] 通知不超过预算且不重复。
- [ ] 模型上下文可解释。
- [ ] 主动提醒失败不影响核心功能。

## Phase 5：正式分发所需的后端

- [ ] 支持单用户日限额和全局熔断。
- [ ] 日志默认脱敏，不记录完整聊天、地址、健康或支付信息。

**依赖：** Task 8  
**预计工作量：** 3 天

### Task 16：客户端切换到后端代理

**描述：** 增加登录/匿名设备身份，将模型和语音请求改为调用 `NomiGateway`；自带 Key 仅保留为开发者选项。

**验收标准：**

- [ ] 新用户不填写 Key 也能完成一次完整对话。
- [ ] 网络失败、额度不足和服务不可用都有独立提示。
- [ ] 退出登录能清除本机令牌，但不误删用户可导出的记忆。

**依赖：** Task 15  
**预计工作量：** 2 天

### Checkpoint F：后端接入

- [ ] 普通用户可无 Key 使用。
- [ ] 客户端无长期服务端密钥。
- [ ] 限额、熔断和脱敏日志有效。
- [ ] 后端故障时 App 仍保留本地规则能力。

## Phase 6：附近服务与预订工具

目标：先完成可验证的查询和跳转闭环，不直接做自动支付。

### Task 17：接入附近美食和酒店查询

**描述：** 新增 `PlaceTool`，调用正式地图/POI 服务，支持位置、半径、预算、评分和营业状态。

**验收标准：**

- [ ] 只有拿到位置授权或用户指定地点后才查询。
- [ ] 结果包含来源、距离、价格区间和更新时间。
- [ ] 没有库存或价格时不显示猜测值。
- [ ] 至少显示一个可打开官方地图或平台的入口。

**验证：**

- [ ] 测试无定位、无结果、接口超时和位置变化。
- [ ] 用真实网络在三个不同地点完成查询。

**依赖：** Task 10、Task 16  
**预计工作量：** 3 天

### Task 18：实现预订预览和官方页面跳转

**描述：** 用户选定酒店、餐厅或票务结果后，生成统一预览，再跳转到官方 App/网页完成预订。

**验收标准：**

- [ ] 预览包含项目、时间、价格、平台和退改说明。
- [ ] 跳转前必须点击“继续预订”。
- [ ] 关闭或取消跳转不会留下待支付订单。
- [ ] App 内不声称“已订成功”，除非收到平台明确结果。

**依赖：** Task 17  
**预计工作量：** 2 天

### Task 19：为正式预订接口预留状态机

**描述：** 定义报价、锁单、订单、支付、核验、取消和退款状态，但默认不启用自动支付。

**验收标准：**

- [ ] 所有写操作有幂等键。
- [ ] 支付超时先查订单，不直接重试。
- [ ] 订单状态只能由业务接口确认。
- [ ] 未取得正式合作接口前，生产配置保持关闭。

**依赖：** Task 18  
**预计工作量：** 1～2 天

### Checkpoint G：工具闭环

- [ ] 用户可以从一句话走到酒店/餐厅/票务官方页面。
- [ ] 查询结果全部有来源和时间。
- [ ] 未发生未经确认的预订或支付。
- [ ] 失败场景可恢复。

## Phase 7：真机验收与发布

目标：证明它在真实生活中可靠、少打扰、值得继续使用。

### Task 20：建立 Agent 回归测试集

**描述：** 收集至少 60 条真实中文指令，覆盖正常、含糊、冲突、权限拒绝、断网和恶意输入。

**验收标准：**

- [ ] 每条用例有期望意图、工具、是否需要确认和最终状态。
- [ ] 高风险用例 100% 不得未经确认执行。
- [ ] 模型或规则变更后能在 CI/本地一键回归。
- [ ] 记录错误原因，不只记录通过率。

**依赖：** Task 8、Task 19  
**预计工作量：** 2 天

### Task 21：真机连续使用 14 天

**描述：** 冻结新功能，自己和至少 2 位测试用户连续使用两周。

**记录指标：**

- [ ] 每日主动打开次数。
- [ ] 完成任务数和失败任务数。
- [ ] 建议采纳率和通知关闭率。
- [ ] 每次误判、误删、幻觉或重复操作。

## 暂不做

- 多 Agent 协作；
- 自动支付；
- 无官方接口的“全自动抢票”；
- Android 同步开发；
- 大规模向量数据库；
- 在没有真机验证前继续扩展页面数量；
- 同时维护两套会漂移的 PWA 和 Swift 业务规则。

## 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 暴露真实服务密钥 | 账号被盗刷、费用损失 | 立即轮换，后端代理，历史清理 |
| 模型误判目标对象 | 删除错误日程或产生错误订单 | 精确匹配、确认卡、幂等执行 |
| 权限请求过早或过多 | 用户拒绝授权、删除 App | 功能触发时逐个申请，允许降级 |
| 模型幻觉实时信息 | 用户误信错误酒店、价格或车次 | 实时数据只来自工具，卡片标来源和时间 |
| 预订接口不可得 | 无法全自动下单 | 第一版只做到查询和官方页面跳转 |
| 后台静音音频 | 高耗电、审核风险 | 公开版移除，保留为侧载实验 |
| 没有测试就重构 | 行为和界面同时回归 | 先建测试底座，每个 Checkpoint 必须验证 |

## 开工建议

从 Task 1 开始，不要先改界面。Task 1～5 完成后，Nomi 才具备继续扩展 Agent 的安全基础；然后再做 Agent 拆分和产品收敛。
